## TASK: Implement Queue + Context Caching + Pipeline Architecture

### Architecture Overview

Replace the current fire-and-forget `tokio::spawn` in `mark_paper()` with a channel-based queue and a dedicated background worker.

```
gRPC handler (mark_paper)
    │
    ▼
mpsc::Sender<MarkRequest>  ──►  mpsc::Receiver<MarkRequest>
    │                                    │
    │ returns accepted=true              ▼
    │                            Background Worker (single loop)
    │                                    │
    │                            ┌───────┴───────┐
    │                            │  Pipeline:     │
    │                            │  - Prefetch    │
    │                            │  - Mark        │
    │                            │  - Write DB    │
    │                            └────────────────┘
```

#### 4. Background worker — pipeline with prefetching

The worker is a single async task that runs forever. It implements a two-stage pipeline:

**Stage A (Prepare):** Download scheme images + student answer sheets from S3, create Gemini context cache for the scheme.
**Stage B (Mark):** Use the cached context to mark each student (concurrent, bounded), write grades to DB.

The pipeline overlap: while Stage B runs for request N, Stage A runs for request N+1.

```
fn spawn_marking_worker(rx: mpsc::Receiver<MarkRequest>, gemini: GeminiClient) {
    tokio::spawn(async move {
        let mut rx = rx;
        let mut prefetched: Option<PreparedRequest> = None;

        loop {
            // Get next prepared request (from prefetch or fresh)
            let current = if let Some(prepared) = prefetched.take() {
                prepared
            } else {
                // Block until a request arrives
                let req = match rx.recv().await {
                    Some(r) => r,
                    None => break, // channel closed, server shutting down
                };
                prepare(&gemini, req).await  // may need retry logic here too
            };

            // Try to grab next request (non-blocking) for prefetching
            let maybe_next = rx.try_recv().ok();

            // Run in parallel: mark current + prepare next
            let (mark_result, prepared_next) = tokio::join!(
                mark_and_write(current),         // Stage B for current
                maybe_prepare(&gemini, maybe_next)  // Stage A for next (if any)
            );

            // Handle mark result (log errors, already wrote to DB inside mark_and_write)
            handle_result(mark_result);

            prefetched = prepared_next;
        }
    });
}
```

#### 5. Gemini Context Caching

This is the key consistency improvement. Google Gemini API supports caching a content prefix:

**Create cache:**
```
POST https://generativelanguage.googleapis.com/v1beta/cachedContents?key={API_KEY}

{
  "model": "models/gemini-2.5-flash",
  "systemInstruction": { "parts": [{"text": SYSTEM_INSTRUCTION}] },
  "contents": [{"parts": [scheme_image_parts...], "role": "user"}],
  "ttl": "600s"
}
```

Response includes a `name` field like `"cachedContents/abc123"`.

**Use cache in generateContent:**
```
POST https://generativelanguage.googleapis.com/v1beta/models/gemini-2.5-flash:generateContent?key={API_KEY}

{
  "cachedContent": "cachedContents/abc123",
  "contents": [{"parts": [student_images + final_instruction], "role": "user"}],
  "generationConfig": {"responseMimeType": "application/json", "temperature": 0}
}
```

Note: when using cachedContent, do NOT include systemInstruction or the scheme images in the generateContent call — they're already in the cache.

**Delete cache (cleanup):**
```
DELETE https://generativelanguage.googleapis.com/v1beta/cachedContents/{id}?key={API_KEY}
```

#### 8. Retry logic (3 attempts)

Every Gemini API call (cache creation, per-student marking) should retry up to 3 times with exponential backoff:
- Attempt 1: immediate
- Attempt 2: wait 2 seconds
- Attempt 3: wait 4 seconds
- After 3 failures: log error, skip this student (for marking) or fall back to non-cached mode (for cache creation)

For the overall mark_and_write flow:
- If cache creation fails after 3 retries, fall back to the non-cached `mark_paper()` method (which still works, just without caching benefits)
- If individual student marking fails after 3 retries, skip that student and continue with others. Log which students failed.
- Write whatever successful grades we have to DB (partial success is fine — better than all-or-nothing)

#### 9. Cleanup

After all students in a request are marked and grades written to DB:
- Delete the Gemini context cache (fire-and-forget, don't retry)
- Log completion
